# 外部の測定記録・校正情報を入力元にする案

状態：検討メモ。2026-11-21時点で実装は保留。もう少し検討してから実装する。

この文書は会話中のアイデアを保存したもので、確定仕様や実装指示ではない。JSONの構造・画面構成・対応付けの規則は未決定。

## 利用者からのアイデア

既存の「入力元」に、外部の校正情報／測定記録を選ぶ入口を追加する。

考えている入力元は次の2つ。

1. 他の`.cutp`で計算した校正値と不確かさを参照する。モデルをモジュールとして再利用できるようにする。
2. 自動測定ソフトからJSONを書き出し、このツールから参照する。JSONには、主にType A評価用の測定値と、使用した標準器の校正値・不確かさ情報を列挙する。

測定結果や測定点が変わっても、対応するデータがある場合に参照できる仕組みを考える。毎回モデルの対応付けを作り直す手間を減らし、将来の日常校正への利用につなげたい。

## 現状の確認

- `.cutp`にはモデル・入力値・評価条件を保存している。算出結果一式は他モデルへ渡すための保存対象になっていない。
- 現在の「入力元」はType Aの回帰推定値や測定表の列の平均に接続する仕組み。外部の評価済み校正値を扱う場合には、この制限を見直す必要がある。
- プロジェクト内の参照値・参照式、測定表、評価済み統計量の入力、画像同梱の仕組みは既にある。

## 会話中の設計案（未確定）

測定ソフトのJSONと、このツールの計算結果出力を、共通の受け渡し形式に載せる案がある。まず外部JSONの受け取りを検討し、他の`.cutp`の結果も同じ形式へ出力することで、入力元の扱いを共通化できる可能性がある。

受け渡す情報として、次の区別を検討する。

| 情報 | 内容の候補 |
|---|---|
| 測定記録 | 観測値の列・観測組、単位、測定点、測定条件 |
| 校正情報 | 校正値・補正値、単位、不確かさ、自由度、証明書・標準器の識別情報 |
| 使用関係 | どの測定記録に、どの標準器・校正情報を使ったか |

入力元の来歴と、不確かさの評価方法は独立して扱う案。外部データという理由だけでType Bに固定しない。他モデルの出力にはType A・Bを合成した不確かさもあり得る。

## 次に検討する論点

- **対応付け**：表示名や配列順ではなく、何を識別子として使うか。測定点の増減、同じ公称値でのレンジ・周波数・測定機能の違いをどう区別するか。
- **欠落・曖昧さ**：対応なし、候補が複数、単位不一致をどう表示し、計算対象の点をどう選ぶか。「対応するものがあるときだけ参照」の具体的な動作。
- **測定記録と標準器の関係**：点ごとの使用関係で足りるか、同じ点の観測組ごとに標準器や条件が変わる場合も扱うか。
- **不確かさの表現**：標準不確かさと拡張不確かさ・包含係数のどちらを渡すか。自由度や分布の情報が不明な場合の扱い。数値の意味が校正値・補正値・指示誤差のどれかも明示する必要がある。
- **共通要因と相関**：同じ校正値を複数箇所で参照するときの依存関係。同じ証明書の別の校正点を、一律に完全相関とは扱えない。
- **採用内容の保存**：参照元・版・採用データを`.cutp`にも保持するか。外部ファイルの更新後も過去の評価を再現する方法。更新の検出と採用のタイミング。
- **他モデルの結果**：保存済みの評価結果を参照する方式と、参照先モデルを再計算する方式のどこまでを扱うか。結果と計算条件の対応、古い結果の判別も必要。
- **GUI**：入力元の選択、対応状況の確認、採用を、作業者の入力の流れに沿って配置する。JSONの内部構造を利用者へそのまま操作させる必要があるか。
- **形式の管理**：JSONの版、必須項目、数値精度、単位の扱い、既存形式との互換性。

## 実装順序として出た案

共通JSONと対応規則の検討 → 外部入力の選択・確認 → 同形式での計算結果出力 → 必要なら結果の`.cutp`同梱、という順序が提案された。これも未確定であり、実装開始前に見直す。

DBの導入はこの案の前提にしない。今回はメモの保存のみとし、計算処理・保存形式・GUIには変更を加えない。
